## 真 OCR 通道——界面截图 / 密集表格文字（2026-09-11 实战沉淀）

**触发**：阁下说「OCR 读图」「把字读准」，或图是软件界面、参数面板、表格、文档截图。

**正解是真 OCR 引擎，不是视觉模型描述**：本机 venv 自带 `rapidocr_onnxruntime`（跑 `/opt/data/.venv/bin/python3`），输出**带坐标框**的文字块。一条命令 `scripts/ui_ocr.py <图>` 出全图按行聚合结果。

流程：
1. **全图 OCR 拿坐标** → 看文字块落在哪些 x/y 区间
2. **按坐标裁块 + 放大 3~8 倍复核**（`--crop x1,y1,x2,y2 --scale 6 --read`）
3. **视觉模型只负责答「这是什么」**（`bin/ds-vision --desc`）；小字读数一律以 OCR 为准

实测坑（同一张 AssetStudio 界面截图）：
- **视觉模型读界面小字必错**：`avatar_1001_01_full_hx` 读成 `_fx`；`Mip map bias: 0` 整行读成 `0 iseq dew dn`（还带 0.73 置信度）。放大 8 倍后两处都对上——小字先裁再读，别信整图一次过。
- **模型自报的文字位置不可靠，别按它说的裁**：坐标只信 rapidocr 的框。本天使按「预览面板在右边」估 x=620 起裁，把 x≈495-614 的整块参数区切掉，连读三轮「无文字」。
- **别用固定网格硬裁**——先 OCR 定位，再按坐标裁。
- **rapidocr 也会漏块**（漏了 Name 列一行 `async_test.lua`）→ 两边都跑、交叉补全；OCR 给字，视觉模型给「这是什么」和结构上下文。
- **`--json` 落盘是裸 list，键名是 `{x,y,x2,y2,t,s}`（不是 text/txt/content）**——按 `t` 过滤、用 `x/x2/y/y2` 定位争议字块，再拿坐标去裁。（2026-09-11 实战：先按错误的键名过滤，得到空结果，白花一轮）
- **`--crop … --read` 的输出行序会乱，别按它的顺序判读**：同一行被切成多块后返回顺序不保证（2026-09-11：一行「小覃，⑨，苏晴梦璃」返回成 `苏晴梦璃`→`覃`→`9`）。**顺序、行归属一律回全图 JSON 拿**，裁块只用来「凑近看形状」。
- **OCR 给字，视觉模型给符号形状——单字符/符号类要裁块放大终审**：带圈数字、emoji、装饰符会被 OCR 压平（2026-09-11：图上 `⑨` OCR 读成 `9`（丢圈）、`⚠️` 读成 `1`）。这类 token 的**存在与形状**用 6 倍裁块喂视觉模型，读它的笔画描述（「有完整外圈 + 圈内单个数字 9」）才算确证。
- **长图（>4000 px 高）先用 rapidocr 整图跑一遍**：实测 1152×4522 / 37 行全部 ≥0.95 置信度，**不需要分段**——分段是喂视觉模型时的无奈之举（上下文/缩放限制），OCR 能一次拿全。先拿 OCR 全文和坐标，再只对争议块用视觉模型复核，比「四段裁图 + 逐段 vision」又快又准。
- **CDN 图先换尺寸，再谈放大（2026-09-11 实战）**：URL 里带尺寸段的图（QQ 群/用户头像 `p.qlogo.cn/gh/<群号>/<群号>_<seq>/100`、微博 `…/thumb`、`?w=`/`?size=`）——**改 URL 参数取大图，永远优于本地放大**。同一张群头像：100px 版 8× LANCZOS 两轮读出两个**互斥且都错**的答案（「极限生存挑战」/「九球杯群友赛冠军纪录」，还编出 METAL 单独一行）；换 `/640` 一次 OCR 就给出 0.99/0.99/0.91 的稳定读数（「久璃宇杯 / 第四届 / 悟饭合金弹头怀旧赛」）。**缩略图源就是信息上限，放大不产生信息**——先在 URL 上找尺寸参数，找不到再谈放大。
- 放大仍守「小字放大有上限」那条：3~8 倍 + 带整行上下文，别单字裁。
